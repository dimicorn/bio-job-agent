## Add one job by link (2026-11-21)

- `bio-jobs add <url> [--employer NAME]` stores one posting: Greenhouse and Lever via their public single-posting GET endpoints, Ashby and Workable via one read of the public board, all parsed by the discovery adapters; any other https page by one GET (robots, pacing, timeouts and no-redirect policy of discovery) reduced to plain text from `JobPosting` markup or title/heading/main text. No migration: the origin is a `link-<employer>` source with adapter `link`, and its raw posting has disposition `added_by_link`.
- Off-watchlist employers are stored with industry unreviewed. Industry, role, seniority, geography and freshness filters that would exclude the job are reported in `add`, `show` and `review`; the job stays in review and bypasses the score gate. Repeat links report the existing job before any request; probable duplicates join the stored job as another origin. Link origins are never expired by syncs and are left out of `doctor` source health.

## M5: scheduled watch and alerts

- `bio-jobs watch` performs one locked sync → filter → score → alert pass. `watch.min_score` inherits the analyst threshold when unset. New and materially changed content alert once per job/content version, persisted in migration `006_watch.sql`. Profile/provider/weight changes do not themselves re-alert. Rejected, closed and submitted jobs do not alert. Desktop delivery is individual for up to three matches and one summary above that. Every batch has a private gitignored Markdown digest; optional Telegram bot delivery uses the standard library and `.env`, off by default.
- Alert claims and digest bodies are committed atomically. File export resumes after a crash. External attempts are recorded before invoking macOS/Telegram and are never retried automatically: a crash or delivery failure can omit an external message, while preserving the digest and preventing duplicate alerts. This is at-most-once external delivery, not guaranteed receipt.
- Complete successful ATS snapshots retire an origin after two absences; a remaining present origin keeps the job open. Reappearance resets the counter and reopens the job. Failed/partial/rate-limited sources and cooldowns close nothing, and career-page watchers never expire lists. Partial career detail fetches now report partial health. Application state is untouched by rechecks. Closed jobs leave operational queues.
- `doctor` and `stats` expose last complete success, retained last error/time, consecutive failed/partial runs and last complete count per source. Counts are unknown until the first complete sync after this migration.
- `setup.sh` offers a daily/twice-daily LaunchAgent, default no, from the repository plist template. Rendering uses plistlib for XML-safe paths. PATH includes the sibling-style local/Homebrew locations; logs go to gitignored `logs/watch.log`, RunAtLoad is false, and the unload command is printed. Re-running can replace this agent or leave it unchanged. Linux receives a cron entry without modifying crontab.
- The scheduled command is `watch --scheduled`; it calls the existing approved application runner only for `apply.mode: auto`, retaining M4 gates. A database-specific flock covers the entire pass and releases on crash/restart. No Docker, scheduler service, heavy dependency, email or n8n integration was added.
- Validation is offline: alert-once across fresh connections, changed-content re-alert, score thresholds, metadata-only changes, summary/individual osascript mocking, crash recovery, failed delivery, bot chunking, two-snapshot expiry, failure/partial/rate-limit protection, multiple origins, reappearance with submitted state preserved, health output, CLI dispatch, scheduled auto-mode selection, overlap/crash locking, XML-safe daily/twice-daily plist rendering and rerunnable setup with fake launchctl. **No live source sync, live LLM request, real desktop/Telegram notification or real launchd load ran for M5.** **286 offline tests passed, 4 live tests deselected, on Python 3.14.7**; Ruff lint/format checks, `bash -n setup.sh` and `git diff --check` also passed. Of these, 37 tests cover M5 watch and scheduling behavior. Older validation entries below describe their respective historical milestones.

Official documentation reviewed before implementation:

- [Lever Postings API](https://github.com/lever/postings-api): published postings are public and may be collected by third parties; documents GET list, JSON mode, skip/limit pagination and hosted/apply URLs. Only the public global instance is implemented. No authentication is required for the GET feeds used here; the authenticated recruiting API and submission API are unused.
- [Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html): public GET jobs and `content=true`, no GET authentication, source IDs and publication-vs-update distinction. No Harvest API or application POST is used.
- [Mytos careers](https://www.mytos.bio/careers) and [official Lever board](https://jobs.lever.co/mytos) verify the employer/site association and commercial cell-manufacturing/CDMO activity. [Mytos terms](https://www.mytos.bio/terms/) permit internal non-commercial reference; use is limited to a single user's local search. The adapter does not scrape the employer website. Fixtures replace employer prose with synthetic text rather than redistribute it.
- [Isomorphic Labs openings](https://www.isomorphiclabs.com/job-openings), [Greenhouse board](https://job-boards.greenhouse.io/isomorphiclabs) and [recruitment notice](https://www.isomorphiclabs.com/privacy-notice-for-talent-sourcing-and-recruitment) verify the commercial drug-discovery employer and Greenhouse relationship. [Employer terms](https://www.isomorphiclabs.com/terms-and-conditions) cover their own website and third-party links; discovery uses the documented public Greenhouse API. This is local reference, with no public job-description redistribution.

Robots checks (both HTTP 200, also recorded in fixtures):

- [Lever API robots](https://api.lever.co/robots.txt): `Allow: /`, `Crawl-delay: 1` for the generic user agent.
- [Greenhouse API robots](https://boards-api.greenhouse.io/robots.txt): only `/embed/` disallowed; `/v1/boards/.../jobs` allowed.

No public GET quota was specified in the reviewed API documents. The application uses conservative per-host pacing (minimum 1 second, raised for robots crawl-delay/request-rate), a 20-second HTTP timeout and default **900-second** source refresh interval (configurable, with a 60-second lower bound). Lever is paginated at 100 records/page with a 100-page safety cap; an incomplete capped snapshot is refused. There are no automatic retries. HTTP 429 extends the persisted cooldown by at least `Retry-After`; Job endpoint 401/403, redirects, robots 429/5xx and robots network failures stop the source; other robots 4xx responses allow access. Robots decisions are rechecked on each explicit sync. The configured sources have no authentication or application data requirements.

Required fields: source posting ID, title, and public HTTPS source/apply URL; employer identity comes from the reviewed source configuration. Location/description are optional facts (unknown location is labelled for review); missing required fields make only that posting malformed, preserving source processing with `partial` health. Each employer needs a unique source ID, correct board token, reviewed industry classification and evidence URL in YAML.

Fallback for either source: retain cached listings and source error/last-seen information; use the [Mytos board](https://jobs.lever.co/mytos) or [Isomorphic board](https://job-boards.greenhouse.io/isomorphiclabs) manually, and refresh after restrictions clear. Do not bypass blocked access. No manual URL import or alert ingestion is implemented in M1.
